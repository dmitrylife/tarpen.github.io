# Tarpen — руководство по работе с сайтом

Это практическое руководство для ведения общественного архива Tarpen.

Сайт построен на Jekyll. Основные данные хранятся в Markdown-файлах кейсов в каталоге `_cases/`. После изменений в ветке `main` GitHub Actions автоматически собирает сайт и публикует его на GitHub Pages.

Главный принцип работы:

> Документы подтверждают движение обращения. Фактические изменения определяют состояние проблемы.

---

## 1. Что где находится

Основные каталоги и файлы:

```text
_cases/                  кейсы
_layouts/                шаблоны страниц
_includes/               общие части сайта
img/                     фотографии
  <case>/                исходные фотографии кейса
  <case>/result/         повторная фотофиксация / результат
docs/                    PDF и другие документы
  <case>/files/          обращения, описи, ответы и т. п.
index.html               главная страница
documents.html           сводная страница документов
photos.html              сводная страница фотографий
responses.html           ответы и фактические результаты
author.html              страница «Об авторе»
_config.yml              конфигурация Jekyll
.github/workflows/       автоматическая публикация сайта
Gemfile                  зависимости Jekyll
MANUAL.md                этот файл
```

Обычная работа с сайтом почти всегда сводится к редактированию одного файла в `_cases/` и добавлению фотографий или документов.

---

## 2. Перед началом работы

Перейти в локальную копию проекта:

```bash
cd ~/www/tarpen.github.io
```

Получить актуальное состояние с GitHub:

```bash
git checkout main
git pull origin main
```

Проверить состояние:

```bash
git status
```

Перед редактированием желательно видеть:

```text
Текущая ветка: main
нечего коммитить, нет изменений в рабочем каталоге
```

---

## 3. Как устроен кейс

Каждый кейс — отдельный Markdown-файл:

```text
_cases/<slug>.md
```

Например:

```text
_cases/tushino-bridge.md
_cases/road-access.md
_cases/trees.md
```

В начале файла находится YAML-блок между `---`. В нём хранятся структурированные данные, которые Jekyll использует для автоматической генерации страниц.

После второго `---` находится обычный текст описания ситуации.

---

## 4. Шаблон нового кейса

Для нового кейса можно создать файл по этому шаблону:

```yaml
---
title: Название проблемы
slug: example-case

location:
  settlement: Тушино
  municipality: Неманский муниципальный округ
  region: Калининградская область
  address: описание места

classification:
  category: infrastructure
  featured: true
  order: 40

publication:
  first_published: "2026-09-13"
  updated: "2026-09-13"

summary: >
  Краткое нейтральное описание зафиксированной ситуации.

case_status:
  code: open
  label: Проблема сохраняется
  updated: "2026-09-13"

findings:
  - Первый установленный факт.
  - Второй установленный факт.

evidence:
  photos:
    - src: /img/example-case/photo-1.jpg
      alt: Краткое описание изображения
      caption: Фото 1 — что именно зафиксировано.

interactions: []
observations: []

timeline:
  - date: "2026-09-13"
    text: Проведена первичная фиксация состояния объекта.
---

Здесь размещается основной текст кейса обычным Markdown.
```

Имя файла, `slug` и каталог фотографий лучше делать одинаковыми по смыслу.

## 5. Статус кейса

`case_status` описывает фактическое состояние проблемы, а не состояние переписки с органами власти.

Примеры:

```yaml
case_status:
  code: open
  label: Проблема сохраняется
  updated: "2026-09-13"
```

```yaml
case_status:
  code: monitoring
  label: Взято на контроль
  updated: "2026-09-13"
```

```yaml
case_status:
  code: resolved
  label: Работы выполнены
  updated: "2026-09-13"
```

Не нужно ставить `resolved` только потому, что получен официальный ответ. Кейс считается решённым, когда это подтверждается фактическим состоянием объекта.

---

## 6. Первичная фотофиксация

Фотографии исходного состояния помещаются, например, сюда:

```text
img/example-case/photo-1.jpg
img/example-case/photo-2.jpg
```

И перечисляются в `evidence.photos`:

```yaml
evidence:
  photos:
    - src: /img/example-case/photo-1.jpg
      alt: Повреждение дорожного покрытия
      caption: Фото 1 — повреждение дорожного покрытия.
```

`alt` — короткое описание изображения для доступности и поисковых систем.

`caption` — подпись, которую увидит посетитель сайта.

Если существует внешний архив материалов, можно добавить:

```yaml
evidence:
  archive_url: https://...
```

## 7. Как добавить обращение

Все обращения, заявления и другие контакты с организациями хранятся в `interactions`.

Пример отправленного обращения:

```yaml
interactions:
  - id: appeal-001
    type: appeal
    title: Обращение по вопросу состояния дороги
    authority: Администрация Неманского муниципального округа
    channel: russian-post
    created: "2026-09-13"
    submitted: "2026-09-14"
    document_url: /docs/example-case/files/obrashchenie.pdf
    inventory_url: /docs/example-case/files/opis.pdf
    responses: []
```

Основные поля:

- `created` — дата подготовки документа;
- `submitted` — дата фактической отправки;
- `document_url` — само обращение;
- `inventory_url` — опись вложения, если имеется;
- `responses` — полученные официальные ответы.

Каналы (`channel`), используемые в проекте:

```text
russian-post
email
gosuslugi
web-form
personal
```

Если обращение только подготовлено, но ещё не отправлено, поле `submitted` не указывать.

---

## 8. Подтверждение отправки или регистрации

Если имеется трек-номер, номер регистрации или иное подтверждение:

```yaml
confirmation:
  type: tracking
  value: "12345678901234"
```

или:

```yaml
confirmation:
  type: registration
  value: "ОБР-12345"
```

Не следует выдумывать подтверждение, если его нет.

---

## 9. Как добавить официальный ответ

Официальный ответ добавляется внутрь соответствующего `interaction` в массив `responses`.

Пример:

```yaml
responses:
  - date: "2026-09-20"
    authority: Администрация Неманского муниципального округа
    title: Ответ на обращение
    document_url: /docs/example-case/files/response-2026-09-20.pdf
    summary: >
      Краткое нейтральное изложение содержания ответа.
```

Если известно лишь, что письмо направлялось, но самого текста ответа нет, нельзя реконструировать его содержание. Это можно указать в `note`, а `responses` оставить пустым:

```yaml
note: >
  По имеющимся сведениям официальный ответ направлялся почтовым отправлением,
  однако текст ответа в распоряжении Tarpen отсутствует.
responses: []
```

## 10. Повторная фиксация

Повторные осмотры и изменения на объекте записываются в `observations`.

Пример:

```yaml
observations:
  - date: "2026-09-25"
    type: follow-up
    title: Повторная фиксация состояния
    summary: >
      При повторном осмотре установлено, что состояние объекта не изменилось.
```

Если есть фотографии результата:

```yaml
    photos:
      - src: /img/example-case/result/photo-1.jpg
        alt: Состояние объекта после выполнения работ
        caption: Фото 1 — состояние объекта после выполнения работ.
```

Файлы рекомендуется складывать в:

```text
img/example-case/result/
```

---

## 11. Хронология

Каждое значимое событие желательно добавлять в `timeline`:

```yaml
timeline:
  - date: "2026-09-13"
    text: Проведена первичная фотофиксация.
  - date: "2026-09-14"
    text: Обращение направлено в администрацию.
  - date: "2026-09-25"
    text: Проведена повторная фиксация состояния объекта.
```

Хронология кейсов автоматически попадает и в общую хронологию сайта.

---

## 12. Обновление даты публикации

При содержательном изменении кейса нужно обновить:

```yaml
publication:
  updated: "YYYY-MM-DD"
```

Дата `publication.updated` используется сайтом в том числе для определения даты последнего обновления всего архива.

`first_published` после первой публикации менять не нужно.

---

## 13. Как добавить документы

Документы конкретного кейса рекомендуется хранить здесь:

```text
docs/<slug>/files/
```

Например:

```text
docs/bridge/files/obrashchenie-most.pdf
docs/bridge/files/opis-most.pdf
```

В Markdown-файле используются пути от корня сайта:

```yaml
document_url: /docs/bridge/files/obrashchenie-most.pdf
```

Не добавлять в публичный архив документы, содержащие персональные данные, которые не должны публиковаться.

---

## 14. Как проверить сайт локально

Первичная установка зависимостей:

```bash
bundle config set --local path 'vendor/bundle'
bundle install
```

Сборка сайта:

```bash
bundle exec jekyll build
```

Если сборка успешна, появится каталог:

```text
_site/
```

Для просмотра сайта локально:

```bash
bundle exec jekyll serve
```

Обычно сайт будет доступен по адресу:

```text
http://127.0.0.1:4000/
```

Остановить сервер:

```text
Ctrl+C
```

Каталоги `_site/` и `vendor/` не должны попадать в Git.

## 15. Публикация изменений

После проверки:

```bash
git status
git add .
git commit -m "Краткое описание изменения"
git push origin main
```

После push GitHub Actions автоматически:

```text
checkout
→ устанавливает Ruby и зависимости
→ выполняет Jekyll build
→ загружает _site
→ публикует GitHub Pages
```

Состояние публикации можно проверить в репозитории во вкладке `Actions`.

Рабочий workflow:

```text
.github/workflows/jekyll.yml
```

GitHub Pages должен использовать источник:

```text
GitHub Actions
```

## 17. Что генерируется автоматически

Не нужно вручную добавлять карточку нового кейса на главную страницу.

На основе `_cases/*.md` автоматически формируются:

- карточки кейсов на главной;
- страницы отдельных кейсов;
- общая хронология;
- сводка документов;
- сводка фотографий;
- официальные ответы;
- фактические результаты;
- дата последнего обновления архива.

То есть основной объект редактирования — сам файл кейса.

---

## 18. Что лучше не менять без необходимости

Не следует при обычном наполнении архива редактировать:

```text
_layouts/
_includes/
style.css
_config.yml
.github/workflows/jekyll.yml
index.html
documents.html
photos.html
responses.html
```

Это инфраструктура сайта. Её меняют только когда требуется изменить поведение или внешний вид всего проекта.

## 19. Редакционные правила Tarpen

При публикации материалов:

1. Отделять наблюдаемый факт от предположения.
2. Не приписывать действия конкретному исполнителю без документального подтверждения.
3. Не пересказывать отсутствующие документы по памяти или предположению.
4. Даты отправки, регистрации и ответа указывать только при наличии оснований.
5. Официальный ответ и фактическое состояние объекта считать разными сущностями.
6. При изменении состояния делать повторную фотофиксацию.
7. Сохранять историю кейса даже после устранения проблемы.
8. Формулировать выводы нейтрально и проверяемо.

## 20. Минимальный рабочий цикл

Для обычного обновления существующего кейса достаточно:

```text
1. git pull
2. добавить фото/документ
3. изменить _cases/<case>.md
4. обновить publication.updated
5. добавить observation / interaction / response / timeline при необходимости
6. bundle exec jekyll build
7. проверить страницу
8. git add .
9. git commit
10. git push origin main
11. проверить GitHub Actions и опубликованный сайт
```

Для нового кейса:

```text
1. создать _cases/<slug>.md
2. заполнить YAML по шаблону
3. добавить исходные фотографии
4. добавить документы, если есть
5. локально собрать сайт
6. проверить страницу кейса и автоматические сводные страницы
7. commit + push
```

## 21. Если сайт после публикации выглядит неправильно

Сначала проверить GitHub Actions.

В успешной сборке должны присутствовать этапы, включающие:

```text
Checkout
Setup Pages
Setup Ruby
Build with Jekyll
Upload artifact
Deploy to GitHub Pages
```

Если на сайте видны конструкции вида:

```text
{% ... %}
{{ ... }}
```

значит Jekyll-шаблоны не были обработаны и опубликован исходный код. В текущей конфигурации этого не должно происходить, потому что публикация выполняется явным workflow `.github/workflows/jekyll.yml`.

## 22. Резервная копия

GitHub является основной удалённой копией проекта, а локальный Git-репозиторий — рабочей копией.

Для актуализации локальной копии достаточно:

```bash
git pull origin main
```

Дополнительно можно периодически создавать отдельный архив каталога проекта, но Git уже хранит историю всех закоммиченных изменений.

---

## Короткое правило

Если меняется конкретная ситуация — редактируем кейс.

Если меняется устройство всего сайта — редактируем шаблоны или инфраструктуру.

В большинстве случаев для ведения Tarpen достаточно одного Markdown-файла кейса, фотографий и подтверждающих документов.
